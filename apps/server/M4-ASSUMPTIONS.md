# M4 server: shapes and rules that are NOT observed

Design choices for the M4 server slice. Clock and time zone are injected (`Service.now()`, stored `settings.timeZone` and `startDayOfWeek`); all day arithmetic is on calendar dates, never `+86400000`.

## Sync
- `batch/check` is unchanged (consumes columns, groups, profiles, filters, tags, order beans, tasks, checks, remindChanges): no habit, focus or countdown key. These entities sync through their own endpoints: `GET /habits` (full list), `POST /habitCheckins/query {habitIds, afterStamp}`, `GET /pomodoro/record/{cp}` (delta), `GET /countdown/list` (full list). Keeping the envelope schema fixed also preserves verbatim `buildCheck(0)` snapshot round-tripping.
- Task `focusSummaries` is kept by the server when focus records change; the touched task gets a new `seq` (it shows up in the next delta) but no new etag.

## Habits
- Request and response of the unobserved ones: `POST /habitCheckins/query` -> `{checkins: {habitId: [checkin]}}` (every requested id is a key); `afterStamp` is inclusive (`checkinStamp >= afterStamp`). `POST /getHabitRecords {habitIds, afterStamp}` -> `{habitRecords: {habitId: [record]}}`; `POST /habitRecords {add,update,delete}` -> `{id2etag,id2error}`. A habit "record" is the per-day log with a note (HAB-801): `{id, habitId, checkinStamp|stamp, content, mood...}`, stored verbatim.
- Batch codes: `EXISTED`, `NOT_EXISTED`, `habit_not_exist` (check-in or record for an unknown habit), `DuplicateCheckinException` (second check-in for the same habit and day, also when an update moves a row onto an occupied day), `UNKNOWN` (invalid `checkinStamp`, later than tomorrow in the user's zone, or invalid habit status). `NoHabitPermissionException` and `NO_HABIT` are defined, never emitted (single user).
- Check-in ages are unlimited (HAB-025, "NoorTasks unlimited"). Note length is not enforced (limits table says unlimited).
- A check-in `status` 2 is done. Boolean habit: status as sent, 2 when absent. Real habit: status is forced to 2 when `value >= goal`, otherwise 1 if the client sent 1, else 0 (HAB-014).
- Counters `totalCheckIns`, `currentStreak`, `maxStreak` are server owned: recomputed after every check-in or habit write, and on `GET /habits` when the calendar moved them. They do not change etag or modifiedTime.
- Streak rule (HAB-023 is unverified in the source): a done day extends the run; a due day without a done check-in breaks it, except today; days that are not due, and `exDates`, neither extend nor break. A done check-in on a day that is not due still extends the run. Cadences: `FREQ=DAILY;INTERVAL=n` due every n days from the anchor; `FREQ=WEEKLY;BYDAY=...` (weekly `INTERVAL` honoured), monthly (`BYMONTHDAY`, short months use the last day) and yearly are supported. `TT_TIMES=n` (n per week): every day can fill the quota; the streak counts whole weeks: a week that met the quota adds its done days, a past week that missed resets the run, the running week never breaks it. Anchor = `targetStartDate`, else the creation day (earlier of that and the first check-in). `maxStreak` is the best run ever.
- `GET /habits/statistics/week/current`: seven keys from today (observed), `totalHabitCount` = active (status 0) habits due that day or already done that day, `completedHabitCount` = done that day. Archived habits are left out.
- Deleting a habit deletes its check-ins and records; deleting a section moves its habits to `sectionId "-1"`. No default sections are seeded (defaults to `[]`).

## Focus
- Times are stored exactly as sent (epoch ms numbers or server date strings; both parsed). `pauseDuration` and `adjustTime` are seconds. Active time = span - pause + adjust.
- Records are never rejected for overlapping. Overlap rule for every duration (statistics, heatmap, clock): sorted by start, the part of a record already covered by an earlier record counts once; counts of pomodoros still count each record. Two devices recording the same session therefore double the count but not the minutes.
- `pomodoro`/`pomodoro/timing` batch: `UNKNOWN` for an unparsable time or end before start. Single `DELETE /pomodoro/{id}` of a missing record is 404; `DELETE /pomodoro {data:[ids]}` -> `{deleted, id2error}`; `DELETE /pomodoro/all` -> `{deleted}`.
- `GET /pomodoros(/timing)?from&to`: records whose start lies in [from, to], ascending; `from`/`to` are ms or date strings. `GET /pomodoros/timeline?to=`: both types, newest first, 50 per page, starts before `to` (0 or absent = no bound). `GET /pomodoro/record/{cp}`: `{checkPoint, pomodoroRecords: [..] | null}`, deleted records come as `{id, type, deleted: 1}`, `checkPoint` moves only when focus records change (a fresh database answers `{checkPoint: <cp>, pomodoroRecords: null}`). `POST /pomodoro/filter` body keys: `from, to` (start, ms), `minDuration, maxDuration` (minutes), `linked: "linked"|"unlinked"`, `type, taskId, habitId, timerId, projectId`. `GET /pomodoro/bind/recent` -> up to ten distinct `{type (owner 0/1/2), id, title?, projectId?, lastFocusTime}` newest first. `GET /pomodoros/task?taskId` -> records bound to the task.
- `focusSummaries` on a task: `[{userId, estimatedDuration, estimatedPomo, pomoCount, pomoDuration, stopwatchDuration, focuses: [[recordId, startMs, minutes]]}]` (minutes; slot 1 of a focuses tuple is the start time, an assumption).
- Timers: `GET /timer` (all, archived too), `POST /timer` takes one timer object (create, or update when the id exists; an id is minted when absent) or a `{add,update,delete}` batch; extra `DELETE /timer/{id}`. Archive = `status 1` + `archivedTime`. `GET /timer/overview/{id}` -> `{id, name, totalCount, totalDuration, todayCount, todayDuration, lastFocusTime}` (minutes). `GET /timer/timeline/{id}?to=` like the pomodoro timeline. `GET /timer/statistics/{a}/{b}/{c}/{d}`: the four segments are the timer id, two `YYYYMMDD` stamps and a unit (`day|week|month|year`) in any order -> `{id, unit, from, to, timezone, buckets: {bucketStart: {count, duration}}, totalCount, totalDuration}`.
- Focus ops (`POST /batch/focusOp`, also served at `/focus/batch/focusOp`): body `{ops|opList|add: [...]}` or a bare array, plus optional `since`; each op `{id, oId (session id), op, time (ms), oType?, deviceId?, ...}`. Ops: `start`, `pause`, `continue` (`resume`), `finish`, `exit`/`drop`, `workFinish` (+1 pomodoro), `autoPomoStart`; others are logged only. Response `{checkPoint, current, ops (log entries after `since`, with n), finished}`. `GET /batch/focusOp?since=n` polls the same state. Idempotent by op id. Ops of one push apply in time order. A `start` for another session replaces the running one and a server `exit` op (`reason: "replaced"`) is logged so followers drop it (FOC-801). `current` has the 4.13 fields (`fragments, pauseDuration, duration, sumOfPomo, ...`, times in ms) plus `status` `running|paused`; a running timer reports `duration` up to now. The server does not create the focus record; the client pushes it via `/batch/pomodoro`.

## Countdown
- `GET /countdown/list` (all, archived too), `POST /countdown/batch`. Defaults on add: type 4, status 0, timerMode 0, daysOption 0, `dateDisplayFormat "day"`, style `normal`, reminders `["TRIGGER:P0DT9H0M0S","TRIGGER:-P2DT15H0M0S"]`. One pin slot: a new or changed `pinnedTime` unpins every other countdown; an unchanged pin sent back does not claim the slot. Archive sets `archivedTime`.

## Statistics (computed from stored data; today, zone and week start come from the injected clock and settings)
- A task counts as completed on the day of `completedTime` in the user's zone; won't-do, trashed and note tasks never count. Due day = `dueDate` (else `startDate`); all-day tasks use their own time zone. Class of a completion: no due date = `noTime`; on time = completed at or before the due moment (all-day: on or before the due day); else `overdue`. `notCompleteCount` of a day = open tasks due that day, only for days up to today. `taskByDay` is the last 7 days, `taskByWeek` the last 7 week starts (`startDayOfWeek`), `taskByMonth` the last 7 first-of-month keys (all as observed); values `{completeCount, notCompleteCount}`.
- `task/statistics/{from}/{to}` rows per day; `{t}` one day; `week/{t}/{n}` and `month/{t}/{n}`: n periods ending with the one containing t, `day` = period start. `projectCompleteCounts` keyed by list name (Inbox is "Inbox"), `tagCompleteCounts` by tag `name`, `UNKNOWN_CATEGORY` for untagged. Ranges over 3660 days or invalid stamps are 400.
- Achievement score design: +1 per task created, +3 per task completed, +2 more when completed on time with a due date, -1 on the day after the due day for a task that is still open or was completed after its due day. Cumulative, never below 0, live (today included); `scoreByDay` is the running total at the end of each of the last 7 days. Level thresholds (12 tiers): 0, 100, 500, 1000, 2500, 5000, 10000, 20000, 50000, 100000, 200000, 500000. Focus does not score.
- `statistics/general` focus part: `pomoGoal` from the pomodoro preferences (default 4), `pomoDurationGoal` = preference `focusDuration` or 0. Counts count pomodoros only; durations (whole minutes) add stopwatch records too. `pomoByDay|Week|Month` list only buckets with data as `{count, duration}` (`{}` when empty).
- `v3/user/ranking`: `taskCount` all tasks (no notes, no trash), `completedCount`, `projectCount` lists plus Inbox, `dayCount` days since the first created task inclusive, `ranking` is 0 (percentile needs a population, STAT-004 is parked). `statistics/color`: list name -> colour or null, tag name -> colour or null.
- `pomodoros/statistics/generalForDesktop`: the today/yesterday/total pomodoro fields plus `todayTimingCount`, `totalTimingCount`, goals. `dist/{from}/{to}`: `{from, to, timezone, totalDuration, unboundDuration, projectDurations, tagDurations, taskDurations{id:{title,projectId,duration}}, habitDurations, timerDurations}` in minutes (2 decimals); a record with k bindings gives each an equal share; a record belongs to the day it started. `dist/clock`: 24 hour buckets of minutes; `dist/clockByDay`: day -> 24 buckets; `heatmap`: day -> minutes. Clock, clockByDay and heatmap split a record at local hour boundaries and spread its active time in proportion to the span.

## Summary data endpoint
The "Summary" screen reads `GET /project/all/completed/?from&to&limit=1000` (plus `recentProjectUsers`). That route already existed (M1) and is not capped below 1000; tests were added, no new path.

## Import and export
- New files in the export layout: `habits.json`, `habit-sections.json`, `habit-checkins.json`, `habit-records.json`, `pomodoros.json`, `pomodoro-timing.json`, `timers.json`, `countdowns.json`. Legacy snapshot paths (`captured/api_v2_habits.json`, `api_v2_habitSections.json`, `api_v2_pomodoros_timing__from=*.json`, and `api_v2_countdown_list.json` if present) are claimed as entity sources when no dedicated file exists, and written back to the same path even when empty. Objects are stored verbatim (no counters recomputed, no etag change). Statistics snapshot files and `pomodoro_record_0` stay passthrough documents: they are computed, time dependent values.
- After import, the first `GET /habits` recomputes counters with the rules above, so imported streak numbers may change then; the exporter never recomputes.
