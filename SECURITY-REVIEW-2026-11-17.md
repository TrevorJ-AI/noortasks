# NoorTasks security review, 2026-11-17

Reviewed on branch `review/security`, for a small invited group behind public HTTPS and Caddy. Scope: all 32 original files in `apps/server/src`, `docs/configuration.md`, the web renderers for untrusted task/comment/calendar content, and the production dependency graph. Only local fixtures and injected requests were used. No live application was attacked, no deployment was changed, and no credentials or evidence directories were read.

The findings below are fixed unless explicitly marked as a remaining Low item. This is a source review with regression coverage, not a guarantee against every vulnerability or an infrastructure penetration test.

## Authorization and other checks

- The multi-user front authenticates before tenant dispatch. The tenant pre-handler requires the front's raw-request actor, including when request bodies arrive in another asynchronous context. No remotely reachable general auth bypass was found in that dispatch boundary.
- Per-user SQLite/file roots keep unrelated account IDs isolated. The existing isolation suite enumerates every account-app/front route and checks another user's canary data and database fingerprint. Existing sharing tests cover read/comment/write permissions, assignment, revocation, disabled collaboration, moves, ownership transfer, and ID collisions. Comment routes compare the actual task's project to the addressed shared project; naming an unrelated private task through a shared project does not disclose its comments.
- Attachment storage paths derive from validated IDs, not client filenames/paths. HTTP metadata cannot set a server filesystem path. Downloads resolve database rows within the selected account. The server does not unpack uploaded ZIP/XLSX archives, so attachment ZIP bombs are inert downloads; HTTP restore accepts bounded CSV.
- OIDC uses `openid-client` with state, nonce, PKCE and non-repudiation checks. Existing signed mock-provider tests cover wrong/missing/replayed/expired state, browser binding, invalid signature/issuer/audience/expiry/nonce, disabled users, invite enforcement and native PKCE. This review retained those checks.
- Session tokens, pairing tokens and native codes use cryptographic randomness and hashed storage. Native codes are short-lived and single-use; pairing codes expire after ten minutes. Feed tokens use 192 bits and are checked in constant time; reset/cancel and account status are enforced. API/feed responses set privacy headers.
- SQL values use bound parameters. Dynamically selected tables/columns come from internal enums or fixed code. Error handlers return opaque internal errors rather than stacks.
- `pnpm audit --prod --json` reported **0 advisories** across 158 production/optional dependency entries. No lockfile/dependency change was necessary. This is a point-in-time advisory result.

## Remaining Low items and operational limits

- CSV exports intentionally preserve literal task/habit/focus text for backup compatibility. Formula-like text can be interpreted by spreadsheet applications. A reversible spreadsheet-safe export format is a follow-up; open untrusted backup CSV through a text importer, or use the existing XLSX habit/focus exports, which use string cells rather than formulas.
- Task databases and per-account record counts have no total storage quota. Request/upload/work budgets now constrain single operations, but a malicious invited member can still accumulate data over time. Per-user database quotas and aggregate edge traffic budgets remain deployment/capacity work. Keep the invited group small and monitor the data volume.
- Caddy/host configuration was not deployed or audited on the live machine. Keep the Node listener private, enable HTTPS, use `NOORTASKS_SECURE_COOKIES=true`, and use `NOORTASKS_TRUST_PROXY=true` only with a same-host loopback proxy. Explicit transport injections and OIDC's insecure test flag must remain absent from production.
- Changes deliberately refuse private-network calendar/identity endpoints, redirects, compressed upstream responses, sub-daily ICS recurrence, and over-budget requests. Use final public calendar URLs and split large batches/restores. New browser setup needs `NOORTASKS_SETUP_TOKEN`; existing configured admins/sign-in do not.
